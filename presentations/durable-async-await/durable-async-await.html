The talk is about durable async/await. Working hours is the example because it has long waits with decisions between them.

Say the rule once: 09:00 to 17:00 in the recipient's time zone, not ours.

Three requirements, one at a time

  1. Wait for working hours. Hold the text until 09:00 where the recipient is.
  2. Send now or cancel. The sender stays in control.
  3. Follow up if there's no reply within 24 hours.

These three are what every version in the talk has to do. First we write them in plain code, in one process. Then a polling table, BullMQ, and Aiki each handle the same three.

In one process, a wait is a timer

const timer = setTimeout(() => send(message), msUntilWorkingHours(timeZone));

// Cancel:   clearTimeout(timer);
// Send now: clearTimeout(timer); send(message);

In one process: about 3.5 minutes for slides 5 to 8.

"Before we build it with any tool: what does it take to make code wait?" The example's first wait, in one process: a timer until working hours. One wait is one timer, and callbacks are fine for that.

Send now or cancel is easy in memory: clear the timer. The next slides add the follow-up, because that is where it gets hard.

With a reply and a follow-up, each callback has to cancel the other

setTimeout(() => {
  send(message);

  const timer = setTimeout(() => {
    stopListeningForReply();
    send(followUp);
  }, DAY_MS);

  const stopListeningForReply = onReply(() => {
    clearTimeout(timer);
  });
}, msUntilWorkingHours(timeZone));

Wait for working hours, send, wait a day for a reply, and follow up if none comes. Two things can happen after the send, and each one has to cancel the other. onReply is a listener: it returns a function that stops listening. And this is only one decision.

It was a state machine all along

type StateMachine =
  | { state: "waitingForWorkingHours" }
  | { state: "awaitingReply"; timer: NodeJS.Timeout }
  | { state: "replied" }
  | { state: "followedUp" };

let machine: StateMachine = { state: "waitingForWorkingHours" };

function transition(event: "workingHours" | "reply" | "timeout") {
  if (machine.state === "waitingForWorkingHours" && event === "workingHours") {
    send(message);
    const timer = setTimeout(() => transition("timeout"), DAY_MS);
    machine = { state: "awaitingReply", timer };
  } else if (machine.state === "awaitingReply" && event === "reply") {
    clearTimeout(machine.timer);
    machine = { state: "replied" };
  } else if (machine.state === "awaitingReply" && event === "timeout") {
    send(followUp);
    machine = { state: "followedUp" };
  }
}

setTimeout(() => transition("workingHours"), msUntilWorkingHours(timeZone));
onReply(() => transition("reply"));

Each highlighted if is one arrow in the diagram. machine.state is where you are. machine.timer is what you know, and it only exists while you wait for a reply.

Hide this in closures and you get the callbacks from the previous slide. Every event goes through one function, and the story "wait, send, wait, follow up" can no longer be read from top to bottom.

Then point at the line under the diagram: every requirement makes this machine bigger, and the polling table and BullMQ will show the same thing.

async/await: the compiler writes that state machine for you

await setTimeout(msUntilWorkingHours(timeZone));
await send(message);
const reply = await Promise.race([waitForReply(), setTimeout(DAY_MS)]);
if (!reply) {
  await send(followUp);
}

All three versions keep their state in memory.

"async/await didn't remove the state machine. The compiler writes it for you." The race is the same two outcomes as the callbacks: the reply or the timer. This setTimeout is the promise version from node:timers/promises: it resolves with nothing when the time is up, so reply is empty only when the timer won. When TypeScript compiles async/await for older JavaScript, the output is a switch on a state number, much like the previous slide.

Transition: "This is the code you'd love to write. But all three versions keep their state in memory, and a text written at 23:00 waits ten hours in that memory."

The problem: about 1.5 minutes for slides 9 and 10.

True of all three versions: the timer lives in the process's memory, so a deploy or a crash takes it, and the text, with it.

To pause, something has to save where you were and what you knew

This sentence comes back in every part of the talk. In one process the compiler saves it, in memory. From here on the question is who saves it, and where, so that it survives a restart.

Transition: "So you save it somewhere that survives. How would you build that today?"

By hand: about 5 minutes for slides 11 and 12.

The least infrastructure: your database, and something that checks it every few seconds.

The colours say which requirement added each part. Purple came with waiting for working hours: send_at and status. Orange came with send now or cancel: only the cancelled value, no new column. That one is genuinely easy here, so say so. Teal came with the follow-up: follow_up_at and three more statuses.

send_at and follow_up_at are worked out from the recipient's time zone when the row is written. Rows are picked up when one of them has passed, and the webhook sets status to replied.

Point back at the state machine slide: the status values are its boxes. status is machine.state, and the other columns are what it knows. Picking up a due row is calling transition() for it.

If asked "so Aiki is a polling table underneath?": partly, yes. Aiki also keeps each waiting run in your database, with the time it's due, and wakes it then. The difference is that you don't write or maintain that part.

BullMQ: a job for each wait, and a table for replies

new Worker("texts", async (job) => {
  if (job.name === "send") {
    await send(job.data.message);
    await texts.add("follow-up", job.data, { jobId: `follow-up-${job.data.id}`, delay: DAY_MS });
  } else if (job.name === "follow-up") {
    if (await db.hasReply(job.data.id)) {
      return;
    }
    await send(job.data.followUp);
  }
}, { connection });

await texts.add("send", text, {
  jobId: text.id,
  delay: msUntilWorkingHours(text.timeZone),
});
// Inbound SMS webhook
await db.saveReply(textId);

job.name is machine.state, job.data is what it knows, and the worker is transition().

Send now or cancel: get the job by its ID, then promote() or remove().

"Many teams already run a queue like BullMQ, so why poll?" This is not a comparison of tools: it is the same feature, built on a queue.

Point at the two highlighted lines, then back at the state machine slide: the same ifs. A job can't pause halfway through for a day, so each wait becomes its own job: a chain of jobs, one job name per state. And a job can't receive a reply, so the reply goes into a table that db.hasReply reads.

The follow-up job gets its own ID, so a retried send job can't add a second follow-up. Send now or cancel is about the same as Aiki's lookup by reference ID; the one difference is that after the first text has gone out, the job to cancel is the follow-up, under its own ID.

Key line: "Does it feel familiar? It's the state machine slide again, stored in your database or your queue." The waiting was never the hard part. The hard part is several waits with decisions in between, and every new requirement makes the machine bigger.

If asked how this differs from what Redis gives you: BullMQ keeps its state in Redis, so it is as durable as Redis is set up to be. Without persistence, a restart loses it; with snapshots, you lose what came after the last one; with the append-only file, about a second. Any eviction policy other than noeviction can drop job keys when memory runs short, and a text waiting overnight is exactly the kind of key that sits long enough to be dropped. Aiki keeps its state in your database, with that database's transactions.

With Aiki, you write the async/await version

export const textMessageV1 = workflow({ name: "text-message" }).v("1.0.0", {
  async handler(run, input: Text) {
    const waitMs = await msUntilWorkingHours.start(run, input.timeZone);
    await run.sleep("until-working-hours", { milliseconds: waitMs });
    await sendText.start(run, { to: input.to, message: input.message });
  },
});

msUntilWorkingHours and sendText are tasks: Aiki saves each result.

Aiki: about 10 minutes for slides 13 to 17, including the live parts.

"Same three requirements, with Aiki." The room knows them by now: move fast and let the code speak. Compare it with the first two lines of the async/await slide: the same shape, but the wait is run.sleep, and it survives a restart.

The two tasks, if anyone asks:

msUntilWorkingHours runs msUntilWorkingHoursAt(timeZone, Date.now()). Reading the clock is a task, so Aiki records the answer and gives back the same one after a restart. sendText runs await sendSms(text.to, text.message).

If asked whether a text can go out twice: yes, the same as with a retried job. If the app crashes after the SMS call but before Aiki saves the result, the task runs again. If the SMS provider accepts a request ID that blocks duplicates, pass one.

Live: crash it while it waits

The demo page has a form for writing a text, the list of texts sent so far, and two phones: one recipient in New York, one in San Francisco, three hours behind. Each phone shows its local time and is dark outside working hours.

  1. At the bottom of the page, click "Set New York to 08:59:00". The app now believes it is 08:59 in New York, so working hours there open in a minute. Say: "For the demo, working hours in New York open a minute from now. The slides keep 09:00 and 17:00."
  2. Send "Can you send the signed contract today?" to the New York recipient. The text waits, with a countdown to 09:00 in the list. Its History link opens the run in the Aiki dashboard, where it is sleeping.
  3. Crash the app. In the terminal: kill -9 $(lsof -ti tcp:9852 -sTCP:LISTEN). The page says "The app is not running". (Keep -sTCP:LISTEN: without it, lsof also lists the browser.)
  4. Start it again with bun run app. The countdown is still there.
  5. At 09:00 the New York phone lights up and the text arrives, once.

Key line: "Aiki saved where you were and what you knew, in your own database."

Send now, or cancel

When the text is created

await textMessageV1.with("reference.id", "text-2").start(aiki, input);

Later, when the sender clicks a button

const handle = await textMessageV1.getHandleByReferenceId(aiki, "text-2");
await handle.wakeup();                          // send it now
await handle.cancel("The sender took it back"); // or drop it

Live: send one waiting text now, and cancel another

The reference ID is your own ID for the text, so nobody needs to store Aiki's run ID. wakeup() ends the sleep early, and the workflow carries on to the send.

On the demo page, San Francisco is three hours behind New York: when New York opens at 09:00, it is 06:00 there. So a text to the San Francisco recipient would wait about three hours, which is the text to send now.

  1. Send a text to San Francisco, then click "Send now" under it in the list. It reaches the San Francisco phone at once.
  2. Send another to San Francisco and click "Cancel". It shows as "Cancelled" and never reaches the phone. Skip this step if time is short.

Follow up if there's no reply

export const textWithFollowUpV1 = workflow({ name: "text-with-follow-up" }).v("1.0.0", {
  events: { replied: event() },
  async handler(run, input: TextWithFollowUp) {
    const waitMs = await msUntilWorkingHours.start(run, input.timeZone);
    await run.sleep("until-working-hours", { milliseconds: waitMs });
    await sendText.start(run, { to: input.to, message: input.message });

    const reply = await run.events.replied.wait({ timeout: { hours: 24 } });
    if (reply.timeout) {
      await sendText.start(run, { to: input.to, message: input.followUp });
    }
  },
});
// Inbound SMS webhook
await textWithFollowUpV1.events.replied.sendByReferenceId(aiki, textId);

The highlighted lines are all the follow-up added: the event, the wait, and the send. "Remember the race on the async/await slide? run.events.replied.wait({ timeout: { hours: 24 } }) is that race as one call, and it survives a crash."

When a reply comes in, the webhook tells that conversation by its reference ID: one line. Aiki keeps the event with the run until the workflow waits for it, so a reply that arrives early isn't lost.

If asked about a reply that arrives right at the 24-hour mark: every version has to draw the line somewhere, and a reply after it gets the follow-up. In Aiki a wait ends one way, the reply or the timeout, never both, and a later replied event stays with the run for whatever step waits for it next.

What the follow-up cost

Adding the follow-up
Polling tablea migration, three new statuses, a second query, a webhook that writes the row
BullMQa new job type, a replies table, a webhook that writes to it
Aikia few lines in the workflow, one line in the webhook

Live: reply to one text, and let the other time out

Read the table across: the same new requirement in each version. With a polling table or BullMQ, the follow-up changes what you store and the code that reads it. With Aiki, it's a few lines in the workflow and one line in the webhook.

For the demo the reply wait is 30 seconds, not 24 hours. One text at a time:

  1. Tick "Follow up if there's no reply" on the form and send to the New York recipient. Then play the recipient: click "Reply" on the New York phone. The list says "They replied, so no follow-up".
  2. Send another with a follow-up, and this time don't reply. 30 seconds later the follow-up reaches the New York phone.
  3. Open that second text's History link: each step with its recorded result, from waiting to the follow-up.
